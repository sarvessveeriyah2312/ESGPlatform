# White-Label — Implementation Plan

**Status:** Phases 1–5 implemented (see below). Phase 5's account creation and destination-charge wiring are both verified live against real Stripe test-mode calls (see its own section); only a fully completed Connect onboarding (identity/bank details, which this assistant won't submit) remains unexercised. Phase 0 (a real prospective partner) still hasn't happened — this was built ahead of that on explicit instruction; treat it as unvalidated until a real partner exercises it.
**Prepared:** 29 Aug 2026

## Context

White-labeling would let a partner — a sustainability consultancy, an accounting firm, a bank offering it to SME clients — offer EsgEasy under their own brand to their own end customers, who may never know EsgEasy exists underneath. The BRD already identifies a "Consultant" persona managing multiple client accounts; white-labeling is the natural next step beyond that, but it's a distinct capability, not an extension of the existing `CONSULTANT` role.

This document assesses what the current codebase actually supports, what has to change, and a phased path — grounded in the real architecture, not a generic SaaS-white-label checklist.

## Current architecture — what's already there, what's missing

**Working in favor of this:**
- Real multi-tenancy already exists: `Company` is the tenant boundary, enforced at the data-access layer via a Hibernate `@Filter` (`companyFilter`), not just in application code.
- A `CONSULTANT` role already exists for managing multiple client tenants from one login — architecturally adjacent, though it's the *consultant using EsgEasy's own UI*, not *EsgEasy running under someone else's brand*.

**What's missing, confirmed by reading the actual code:**
- **Branding is a single global singleton, not per-tenant.** `PlatformSettings` is fetched via `repository.findFirstByOrderByCreatedAtAsc()` — literally "the first row in the table." There is exactly one brand configuration for the entire platform today.
- **"EsgEasy" is hardcoded in code, not data**, in at least these places (verified directly this session):
  - `MfaService.java`: `private static final String ISSUER = "EsgEasy";` — baked into every TOTP QR code
  - `EmailService.java`: every transactional email (invite, verification, password reset) ends with a literal `"— EsgEasy Reporting Platform"` sign-off
  - `App.tsx`: sidebar logo/name, and `PAGE_TITLES` (browser tab titles) are hardcoded per-route strings
  - PDF export templates (Thymeleaf, under `backend/src/main/resources/templates/pdf/`) — not read line-by-line this session, but given the pattern above, should be assumed to hardcode the brand name too until confirmed otherwise during implementation
- **No domain/subdomain routing.** The frontend is `HashRouter` on a single domain (`/#/path`). There's no mechanism today to resolve "which brand am I" from a hostname.
- **Billing has no partner concept.** Stripe is wired directly from `Company` to `CompanyBillingService`; there's no entity that would own multiple companies and receive a revenue share or referral fee for them.
- **`SubscriptionPlan` is a closed enum** (`STARTER`, `GROWTH`, `ISSUER_READY`) threaded through onboarding, feature gating, and billing. Adding "white-label" as a fourth value here would touch dozens of call sites — this plan deliberately avoids that (see Phase 1).

## Proposed data model additions

- **New `Partner` entity**: `id`, `name` (internal), `brand_name` (customer-facing), `logo_asset`, `primary_color`, `support_email`, `email_from_address`, `subdomain_slug`, `billing_model` (e.g. `revenue_share_pct` or `flat_referral_fee`), `created_at`.
- **`Company.partner_id`** — nullable FK. `null` means "direct EsgEasy customer" (today's entire customer base); a non-null value means the company was provisioned under that partner's brand.
- **Brand resolution becomes partner-scoped instead of global**: the existing `PlatformSettings` singleton either grows a nullable `partner_id` (so a row with `partner_id = null` is today's global default, and a row with a real `partner_id` overrides it for that partner's companies), or is duplicated into a new `PartnerBrandSettings` table that falls back to the existing global one. The former is less invasive — recommended.

- Backend: `Partner` entity, `PartnerRepository`, `PartnerService`, `PartnerController` (`/api/v1/admin/partners`, full CRUD) — gated to `PLATFORM_ADMIN`/`SUPERADMIN` via `@PreAuthorize` on the controller, no partner self-service, exactly as scoped.
- `CompanyService.adminUpdatePartner` + `PATCH /api/v1/admin/tenants/{id}/partner` links/unlinks a company to a partner. `TenantSummaryResponse` now carries `partnerId`/`partnerBrandName`.
- Frontend: a "Partners" section in the platform-admin sidebar (list, create, edit, delete, with a live brand preview in the form), and a partner-assignment dropdown on each tenant's detail page.
- No change to `SubscriptionPlan`, no change to the JWT/security principal — confirmed in practice, not just planned: a company was linked to a partner while staying on its existing `STARTER` plan with no other effect, verified against the database directly.

The other 4 templates share the identical structural pattern but weren't individually re-verified this pass.
- **Scope decision — resolved**: went with the plan's own recommendation. Branding is post-login only; the public marketing site, `/login`, and `/register` stay EsgEasy-branded (no `user` context exists there yet to brand with anyway). Confirmed live — the browser tab read "EsgEasy - Log In" right up until authentication succeeded, then flipped to the partner's brand name.

### Phase 3 — Routing (subdomain-based MVP) ✅ done
- **Not backend Host-header resolution as originally written** — deviated deliberately. The frontend and API are commonly different origins/ports (true in this repo's own local dev: :3000 vs :8080), so the backend's own request Host header often isn't the browser's actual visited hostname at all. Instead: `GET /api/v1/public/brand?subdomain={slug}` (new, unauthenticated) takes an explicit slug, and the frontend resolves that slug itself from `window.location.hostname` (`resolveSubdomainSlug` in the new `useSubdomainBrand` hook) before calling it. Same outcome, works regardless of topology; a same-origin deployment (e.g. the on-prem nginx bundle) could still derive the slug from the Host header upstream if ever wanted.
- `LoginPage.tsx` and `RegisterPage.tsx` call `useSubdomainBrand()` for their own logo/name (distinct from `App.tsx`'s post-login `user.brandName` — pre-login there's no authenticated user yet to read a brand from). `usePageTitle` also checks it as a fallback behind the post-login brand, so the browser tab title is branded pre-login too.
- **Real gap found while building this**: CORS was configured with `setAllowedOrigins` (exact string match only) — this would have silently blocked every partner subdomain in production too, not merely blocked local testing. Fixed the *code* to `setAllowedOriginPatterns`, which supports a wildcard entry while still matching plain origins exactly when no `*` is present.
- **A second, deeper instance of the same gap, found much later** (while investigating "landing page still shows EsgEasy for a partner-linked user") **and only actually fixed then**: the code-level fix above was real, but `esgeasy.cors.allowed-origins` (`application.yml`) — the actual *value* the pattern matcher runs against — was still hardcoded to the single literal `http://localhost:3000`, with no wildcard entry at all. So every cross-subdomain fetch was still silently CORS-blocked (`TypeError: Failed to fetch`, swallowed by `useSubdomainBrand`'s catch block, page just quietly kept the "EsgEasy" default) — this had **never actually worked**, despite this doc previously claiming it was "verified live" here. That verification either wasn't real or was invalidated later without anyone noticing, since the app degrades silently on failure by design (a broken brand fetch shouldn't break the login page) — which is exactly what let this go unnoticed. Fixed the default to `http://localhost:3000,http://*.localhost:3000,https://esgeasy.my,https://*.esgeasy.my`.
- **Also found in the same investigation**: `LandingPage.tsx` (the public marketing page) never called `useSubdomainBrand()` at all, unlike `LoginPage`/`RegisterPage` — so even once CORS is fixed, a partner's client visiting the marketing site on their subdomain still saw plain "EsgEasy" chrome. Fixed by wiring the hook into just the header and footer logo/wordmark (not the testimonials, FAQ answers, or the footer's legal entity name/copyright line — those describe this platform's own claims and actual corporate ownership, not something that becomes true or false depending on whose subdomain the page is viewed from).
- **Verified live, this time for real**: confirmed via direct `fetch()` from the browser console that the brand endpoint returned `TypeError: Failed to fetch` before the CORS fix and `200` after, restarted the backend, hard-reloaded `http://nusantara.localhost:3000/#/` (a normal reload wasn't enough — this origin's module graph needed a fresh fetch) and got real "Nusantara ESG Hub" branding with the partner's actual primary color in both header and footer; bare `http://localhost:3000/#/` correctly still shows plain "EsgEasy". Also re-checked `LoginPage` under the fixed config (it was flagged as unverified above) — `http://nusantara.localhost:3000/#/login` now correctly shows "Nusantara ESG Hub" too, so the CORS fix covers every page using this hook, not just the newly-wired LandingPage.
- Full custom-domain support (partner-owned DNS + TLS, e.g. `esg.partnerbrand.com`) still deferred, per the original plan — unchanged, still meaningfully more infrastructure work than this phase needed.

#### Follow-up — a partner's subdomain is a login boundary, not just a skin
Requested explicitly: "restrict that any account that does not belong to partner cannot login via partner domain, for example platform admin cannot login via partner domain." Until this point, `partnerSlug` was purely cosmetic (which brand to render) — nothing stopped any valid account, including a platform admin, from authenticating on a partner's subdomain.

- `LoginRequest` gained an optional `partnerSlug` field — the same slug `resolveSubdomainSlug`/`useSubdomainBrand` already resolves from `window.location.hostname`, now also sent with the login request itself (`AuthContext.login` resolves and passes it; no change needed to `LoginPage.tsx`, which never touches the request shape directly).
- `AuthService.login` — new `requireDomainMatch(user, partnerSlug)`, called **after** password validation (so a wrong-domain attempt doesn't help enumerate which emails exist — it fails identically to bad credentials up to that point) but **before** the email-verification/MFA branches (so a wrong-domain account can't even start an MFA challenge on that subdomain). Logic: if the slug resolves to a real `Partner`, the authenticating user's *effective* partner — `user.getPartner()` directly for a `PARTNER_ADMIN`, or `user.getCompany().getPartner()` for a tenant user — must match, or the login is rejected with `ForbiddenException` ("This account isn't available on {partner's brand name}'s login page"). A slug that doesn't resolve to any known partner is treated as no restriction at all, same graceful-fallback posture `useSubdomainBrand` already has.
- Deliberately **role-agnostic**, not a `PLATFORM_ADMIN`-specific check: both `PLATFORM_ADMIN`/`SUPERADMIN` (no partner, no company — `effectivePartnerId` always null) and a tenant user or partner-admin belonging to a *different* partner get rejected by the exact same code path. No special-casing needed.
- **Verified live, all four cases**: platform admin on the Nusantara subdomain → rejected with the clear message, correct password and all; the Nusantara partner-admin login on that same subdomain → succeeds; a tenant company user whose *company* (not the user directly) is linked to Nusantara → succeeds via the subdomain too, confirming the company-inherited path works, not just the direct `PARTNER_ADMIN` case; a company with no partner link at all → rejected on the Nusantara subdomain. Also re-confirmed platform admin still logs in normally on the bare domain — no regression to the unrestricted default case.

### Phase 5 — Billing / revenue share — ✅ account creation + destination-charge wiring both verified live (only full onboarding completion still unexercised)
Built at the user's explicit request ("scaffold full Stripe Connect now"). Initially shipped scaffolded-but-unverified; then the user hit a real `HTTP 400` clicking "Connect Stripe Account" live, which led to actually diagnosing and fixing the root cause (see below) rather than it staying a known caveat. What exists:

- `Partner.stripeAccountId` / `Partner.revenueSharePercent` (nullable, migration V82) — a platform admin sets an explicit % per partner; no default percentage is ever invented in code.
- `StripeClient`: `createConnectedAccount`, `createAccountLink`, `retrieveAccount` — same no-SDK, form-urlencoded pattern as the rest of the class.
- `PartnerService.startStripeConnectOnboarding` / `getStripeConnectStatus`, exposed via `PartnerController` (`POST /{id}/stripe-connect/link`, `GET /{id}/stripe-connect/status`), backed by the platform's own Stripe secret key (`PlatformStripeSecretProvider`, extracted from `CompanyBillingService` so both share it).
- `CompanyBillingService.createCheckoutSession` now loads the paying company's `Partner` and, only if both `stripeAccountId` and `revenueSharePercent` are set, adds `subscription_data[application_fee_percent]` / `subscription_data[transfer_data][destination]` as a destination charge.
- Admin UI: Revenue Share % field and a Stripe Connect status/onboarding panel in the partner edit modal (`AdminPartnersTab.tsx`).

**Root cause of the `HTTP 400`, found by temporarily logging Stripe's actual response body server-side (`StripeClient.wrap` — safe to log, Stripe's error payload never echoes back the secret key, only the client-facing message was ever scrubbed):**
1. First real error: *"Platforms in MY cannot create accounts where the platform is loss-liable, due to risk control measures."* — this platform's own Stripe account is Malaysia-domiciled, and Stripe blocks MY platforms from creating accounts where the platform (not the connected account) is liable for losses/refunds/chargebacks, which is what the plain `type=express` param implies by default.
2. Fix attempt 1 — switched to the modern `controller[losses][payments]=stripe` / `controller[fees][payer]=account` params (making the partner's own account liable, not this platform) while keeping `controller[stripe_dashboard][type]=express`. Got a second, different `HTTP 400`: *"When `stripe_dashboard[type]=express`, your platform must collect fees and be liable for negative balances or refunds and chargebacks."* — i.e. Express-dashboard accounts specifically **require** platform liability, which directly contradicts restriction #1. Conclusion: Express accounts are not available at all to a MY-domiciled platform.
3. Fix attempt 2 (the actual fix) — changed `controller[stripe_dashboard][type]` from `express` to `full` (the Standard-account shape: the partner gets their own full independent Stripe Dashboard, not a lightweight Express one). **This succeeded** — verified live: clicked "Connect Stripe Account" in the partner console, got a real connected account (`acct_1U9izhFjlpZSetbl`, persisted to `Partner.stripeAccountId`), and the onboarding link opened a genuine Stripe "Get started with Stripe" page in a new tab. Did not complete the onboarding form itself (entering a password on an external service isn't something this assistant does, even for a Stripe test-mode sandbox) — a human needs to finish that step.
4. Follow-on implication, found and fixed in the same pass: `StripeClient.createLoginLink` (`POST /accounts/{id}/login_links`) is an **Express**-account-only endpoint — now that accounts are Standard-shaped (`stripe_dashboard[type]=full`), that call would have failed once someone finished onboarding and clicked "Open Stripe Dashboard". Removed it (`StripeClient.createLoginLink`, `PartnerService.createMyStripeDashboardLink`, the `/stripe-connect/dashboard-link` endpoint, and its frontend caller) — Standard-account holders log into `dashboard.stripe.com` directly with their own Stripe credentials, so "Open Stripe Dashboard" now just links there.

**Verified live, in order:** revenue share % round-trip (admin sets 15%, persists, reverted) → Connect button surfacing a real `HTTP 400` → root-caused via server-side response-body logging → two fix iterations → real connected account created → real Stripe onboarding page loaded in a new tab → confirmed `Partner.stripeAccountId` persisted in the database → confirmed the console's status pills correctly show "not yet enabled" for an account that exists but hasn't finished onboarding → **the destination charge itself**: registered a fresh test company (`Revenue Share Test Sdn Bhd`), linked it to the connected partner, set revenue share to 20%, then clicked "Pay Now" on its Starter plan — Stripe accepted the checkout session (rendered a real "Subscribe to STARTER Plan — MYR 99.00/month" payment page, which it would have rejected outright had the destination-charge params been malformed) and a temporary log line confirmed the exact outgoing values: `application_fee_percent=20.00`, `destination=acct_1U9izhFjlpZSetbl` — matching the partner's actual connected account and the % just set. Did not submit any card details (stopped at the payment page). Debug logging removed afterward; the test company/user were left in place as sandbox data, same as other test accounts this session.
